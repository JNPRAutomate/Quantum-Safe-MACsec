# First Steps for New Readers

This guide introduces the system from the perspective of an operator who has
not yet worked with its components. It establishes the component boundaries,
the deployment order, and the documents to consult before making changes.

## 1. Understand the key words

- **MACsec** encrypts Ethernet traffic between devices.
- **MKA** is the MACsec control protocol. It authenticates peers and negotiates
  the keys used to protect traffic.
- **QKD** supplies key material generated by a quantum key distribution
  system.
- **KME** exposes key material and matching identifiers through the ETSI GS
  QKD 014 API.
- **QKD orchestrator** generates and deploys the configuration that connects
  the KME service to the routers.
- **On-box runtime** is the generated Python program running on each router.
  It fetches key material, coordinates matching key identifiers with peers,
  and advances the MACsec keyring.

The orchestrators, QKD service, and router runtime are separate components.
They have separate configuration and responsibilities. Start with
[MKA, QKD, KME, and SAE](pqc/mka_qkd_kme.md) for a deeper explanation.

## 2. Learn the deployment order

The normal deployment sequence is:

1. Prepare the device and service inventory.
2. Create or validate the QKD deployment configuration and PKI profile.
3. Prepare the KME host and deploy its service containers and database.
4. Generate the QKD artifacts and deploy certificates and runtime files.
5. Validate both orchestrator deployments and the device-side runtime.
6. Observe key rotation and MACsec health with the operational tools.

The exact procedure is platform- and inventory-dependent. Do not treat example
hostnames, addresses, credentials, or generated runtime files as production
values. Follow the release-specific CLI and configuration guides:

- [QKD configuration generation](qkd/config_generation.md)
- [QKD deploy phases](qkd/qkd_deploy_phases.md)
- [KME first-run guide](kme/first_run_guide.md)
- [Platform differences](qkd/platform_differences_mx_acx_evo.md)

## 4. Before changing a deployment

- Confirm the release and use its matching documentation.
- Check the exact inventory and link ownership; runtime roles are per link,
  not inferred from a physical ring.
- Understand the current certificate profile and trust chain.
- Confirm the active and pending key state on both peers before attempting
  manual recovery.
- Treat router configuration and MKA-confirmed state as runtime authority;
  generated JSON state is transaction/recovery evidence, not a substitute for
  live device state.
- Use the documented validation and rollback steps; do not manually delete
  keys, locks, certificates, or state files without understanding ownership.

See [Troubleshooting and recovery](tools/troubleshooting_and_recovery.md) and
[State and reconciliation](onbox/state_and_reconcile.md) before intervening in
a live rotation.

## 5. Understand what changed over time

The current release is not identical to every historical procedure in the
repository. In particular, transport, identity, certificate, and keyring
designs changed across releases. Read
[Architecture evolution](architecture_evolution.md) for the motivations and
compatibility boundaries, and [Release history](qkd/release_history.md) for
version-specific delivery details.
